# 项目说明

GymTS 是一个时序实验与独立评价框架。它帮助调用方在固定任务、数据可见范围和预算下
运行方法，保存实际证据，再依据独立参考比较结果。算法、模型、Agent、数据源和工具集
都通过公开接口接入；项目接入用来检验框架通用性，最终交付仍是框架本身。

## 要解决的问题

时序实验往往同时包含数据加载、窗口构造、方法调用、环境操作和评分。如果这些步骤
混在某个模型脚本中，更换数据源或模型时容易连任务含义一起改变；发生失败时也难以
确定模型实际看到了哪段数据。标签后到或参考修订后，重复训练/推理又会改变被比较对象。

GymTS 把实验条件和执行事实固定下来，将评价作为独立步骤。例如，两个方法在相同
公开窗口上预测下一时点，未来值到达前的报告明确保留不足证据；未来值登记后，用原
预测重评，得到新报告。比较条件、缺失结果和评分版本可以被检查，原运行不会被重写。

这既适用于数值预测，也适用于时序问答、检测、受控交互或 Agent 任务。每类任务必须
声明自己的输入、输出、允许操作和评价依据；框架不把所有问题强行转换成预测 MAE。

## 两个主模块

**EnvironmentTS 管数据组织与存储、执行与证据。** 它统一登记静态、合成、仿真和外部
live testbed 来源，固定来源版本、数据快照和血缘，并提供公开读取服务。它组织一次 Run，
固定解析后的配置与组件身份，调用 Environment、Task 与 Candidate，保存观测、输入、输出、
回执、错误和清理事实，再把实际采集数据回流为可复用的数据集版本。具体格式、生成器和
服务连接仍由独立适配器处理。

**AutoBenchTS 管评价。** 它登记和解析 benchmark，固定全部预期评价单元，组织必要的
新 Run，再把固定结果与独立参考交给 Scorer，汇总指标、比较和 Gate。`score` 直接读取
旧 Run 创建新报告，不重新运行 Candidate。失败、缺失或尚未开始的单元都留在计划中。

注册、Schema、存储、制品与 DatasetBuilder 是共享公共 SDK 能力，不因此形成第三个
面向业务的主模块。具体实现和 API 见[框架指南](framework.md)与[接口参考](reference.md)。

## 可替换角色

| 角色 | 负责 | 不应带入的耦合 |
| --- | --- | --- |
| Source / Environment | 来源身份、公开数据、时钟、读取/推进/操作、资源释放 | 某个模型的 prompt 或私有评分答案 |
| Task / TaskSession | 任务含义、窗口/回合、公开 TaskInput、输出解释、允许请求 | 按模型或工具名称偷偷改题与评分 |
| Candidate | 算法、模型、流水线或 Agent 的运行与声明支持的学习 | 未授权数据、独立评价参考、直接绕过环境边界 |
| Scorer | 按固定任务合同与独立依据计算领域指标和缺失计数 | 调用被测方法重做答案，或把 gold 交给 Candidate |
| Reader / BenchmarkResolver | 来源读取与 benchmark→原生 EvaluationSpec 的转换 | 另造执行器或报告体系 |
| DatasetBuilder provider | 固定快照到训练制品，校验用途及领域 token/reward/mask | 自动把测评样本变成训练数据 |

一个适配包可以注册多个角色，多个项目也可共享独立领域合同。可替换意味着明确协议
下的兼容替换；不兼容的任务、输出或单位应在校验中被拒绝，不能悄悄转换成另一问题。

## 一次实验与一次评价

| 阶段 | 固定或产生的事实 | 关键区别 |
| --- | --- | --- |
| 准备资源 | 不可变来源、公开视图、用途、参考与资源版本 | 下载/冻结是显式准备工作，不是计划阶段的隐藏副作用 |
| 计划与校验 | 组件描述、版本、Schema、能力与访问范围 | 纯装配不打开数据/模型/凭证，不保证运行资源当前可用 |
| 执行 | 一个 Run 的实际观测、输入、模型输出、操作与错误 | 打开资源后失败也留下 Run 和已有证据 |
| 封存 | RunResult、事件、制品与可选 Snapshot | 保持当时执行事实，不覆盖成后来修订的结果 |
| 评价 | 固定单元、独立参考、评分政策、指标与报告 | completed 不等于证据充分，更不等于质量达标 |
| 重评 | 新参考或政策下的新报告 | 使用同 Run 的原输出，不重新训练或推理 |
| 训练扩展 | 经用途授权的固定快照和训练制品 | 外部后端训练产生新身份，新模型应另做正式评价 |

每个 Run 的实验边界由对应 Task 和配置固定。研究会话可通过父轨迹串联多个 Run，
但父会话与子实验不混成一个不可检查的大结果。领域 profile 会进一步明确单位，例如
HF 的单样本数值预测或仿真的单 episode；不能拿不同任务的指标直接合并比较。

## 数据、时间与独立参考

源样本时间、实际可用时间和决策时点是不同事实。历史数据若缺少实际传输延迟，适配器
应声明假设；实时数据必须保留收到结果的时刻。末状态和末奖励属于实际执行证据，即使
它们恰好出现在实验范围末端，也不能被丢弃或作为再次动作的理由。

公开观测与私有答案分开存储，Candidate 只获准接触本次公开视图。评价专用资源不自动
获得训练或 prepare 授权。缺失标签、未知 reward、无法确定的结束原因都明确保留；
不能为了让报告“有数值”而补零，或缩小原有 eligible 分母。

所有插件当前都是可信的进程内 Python 代码，受限服务是一种 API 访问边界。它不能
阻止恶意 Python 直接访问操作系统；不可信代码需外置隔离方案，见[安全说明](../SECURITY.md)。

## Agent 与工具集的位置

工具集是外部能力提供方，Agent 是调用决策主体。对已有获准输入做计算，可由 Agent
SDK 运行工具并记录 ToolCall；取得新环境数据或产生环境副作用，必须由 Task 生成
请求，经 Runner 检查后调用 Environment，再将结果交回会话。

LibraryTS 是可替换工具集的一种接入，不是 GymTS 内置算法平台。ChatTS、TimeSigma、
Gymnasium、OpenEnv 等也保留各自原生实现与运行依赖。固定动作策略、工具包装或
Research journal 的验收，只证明相应接口和证据，不证明通用自主 Agent 循环已实现。

上位 Research/工作台、模型资产平台、业务 Agent、训练后端与 GymTS 可以协作，但不
被自动内化为核心职责。项目原始分工材料见[文档总目录](README.md)；实际实现边界见
[项目状态](project-status.md)，下一版合同和企业平台设计仍是单独的提案资料。

## 框架如何演进

每次新项目接入，先尝试现有公开合同。如果差异属于格式、原生 API 或领域评分，留在
独立适配器。如果确实缺少公共生命周期、权限、身份或证据表达，记录真实案例、适配器
无法解决的原因、拟改合同和旧项目回归，再修改核心。

阶段性冻结一个版本，让另一个独立项目在不改核心的情况下完成运行、留轨迹、独立
评价和重评。接口数量和项目数量只是中间产物，能否保留真实语义并独立接入才是证据。
本轮四类来源接入的[总验收](reports/environment-acceptance-2026-10-19.json)记录了这种验证。
