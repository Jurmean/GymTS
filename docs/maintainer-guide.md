# 维护与发布准备

本指南描述仓库当前可执行的维护流程，不表示已经发布到 PyPI、已创建正式 release/tag，或远端 CI
已通过。公共开发规则见[贡献指南](../CONTRIBUTING.md)，安全问题见[安全策略](../SECURITY.md)。
核心版本是 0.5.0，规范基线是 1.2.0；项目采用 [MIT License](../LICENSE)，
第三方代码、模型和数据保留各自的来源与许可条件。

## 维护边界

核心只承载通用执行、资源/证据接口和评价。项目放入独立发行包；中立领域合同也可以作为独立包复用，
不因多个项目共享就自动移入核心。维护新接入时先审核领域语义、访问授权、失败证据和重评闭环，
再考虑抽象是否需要上移。[环境接入指南](environment-adapters.md)保留了零核心变更的实际案例。

核心变化需有真实无法表达的需求、适配器无法解决的理由、公共协议变动和旧项目兼容方案。
定期冻结 `gymts/**/*.py` 与 `setup.cfg`，固定 wheel 和源树身份，再让独立项目在不改核心的情况下完成
运行、封存、评价与原 Run 重评。冻结是某轮验收基线，不等于永远禁止修正核心；若打破冻结，应建立新基线
并保留旧证据，不覆盖旧 Run 或把新实现冒充旧修订。

## 版本和兼容性建议

当前没有公开的长期支持或稳定 1.x 兼容承诺。以下为维护建议，正式发布时应在 release notes 中确认采用的政策：

- 0.x 期间，破坏公共配置、协议、导入路径或持久证据读取能力的变化提升次版本，并写迁移说明。
- 补丁版本用于兼容的修复和文档澄清；协议消息和组件修订仍按它们自己的身份管理，不能只改发行版本掩盖内容变化。
- 独立适配包单独版本化，声明实际验证的 `gymts` 兼容范围，避免把所有项目绑为同一发行节奏。
- 固定 ComponentRef、数据 revision、模型实现和参考快照。已经发布的不可变内容不覆盖写入。
- 旧 Run/CAS 保留，重评生成新评价；运行结果不能因换评分器或补标签而原地改变。
- 如果新评分合同不兼容旧消息，应保留旧评分适配包或提供显式转换，不把同一 schema ID 的含义偷偷替换。

0.3.x 到独立项目包的导入/安装变化见根 [README](../README.md)。0.5.0 环境接入验证以
既有冻结源树和 wheel 为基线，新增适配器独立验收；不要仅为了文档发行方便变更核心语义。

本次 MIT 同步只更新许可文本、文档和打包元数据。`setup.cfg` 哈希和新构建 wheel 的身份会变化，
核心 Python 实现与公共合同不因许可同步而改变。旧冻结 wheel、源码身份和实验报告保持原样；
新制品必须记录自己的哈希，不能冒充原验收使用的 wheel。

## 每次 PR 的检查

阅读实际 diff 和关联需求，确认改动没有携带本机实验环境、私有 benchmark、凭证或下载的模型。
检查同仓库适配包没有进入核心 wheel，插件发现不导入项目运行时，显式启用能够重复安全调用。
领域指标的缺失/无效/未知语义必须明确，不能把工程接线通过写成模型质量提升。

按影响范围选择验证。纯文档修改核对链接、命令、版本、代码围栏和标注即可；不要为了凑测试数运行训练。
改变核心或打包后执行下列检查；新增后端还需按其 README 执行有界的原生验收。

```bash
# 环境预先具备 setuptools>=58、wheel、venv/pip；以下检查不访问包索引。
python -B -m unittest discover -s tests -v
python -B scripts/check_release.py --output /tmp/gymts-release-check.json
python -B scripts/check_adapters.py --output /tmp/gymts-adapter-check.json
```

`check_release.py` 构建核心 sdist、直接 wheel、从 sdist 重建 wheel，在源码外的干净环境中安装，
运行核心回归和临时外部插件，并检查归档路径、包内容和一组已知密钥模式。
`check_adapters.py` 自动发现 `adapters/*/pyproject.toml`，分别构建/重建/隔离安装，检查发现不导入、
显式启用、回归、移除后核心运行和旧输出重评，再验证所有包共同启用。共享领域依赖仅从本地 wheelhouse 解析。
这些脚本结束后删除临时发行包，`--output` 只保留 JSON 报告。

已有基线分别是核心 160 项零跳过，以及 11 个独立包 319 项运行、265 项通过、54 项因可选依赖缺失跳过。
新环境适配器另有 58 项完整原生环境测试，详见[总验收](reports/environment-acceptance-2026-10-19.json)。
记录当前实际结果，不把跳过写作通过；现有数量不应作为新增测试必须保持不变的硬指标。
工作流配置了 Python 3.9/3.12/3.13；本机语法解析或单一解释器通过不等于该矩阵已在远端成功运行。

## 证据、凭证和第三方材料

每份原生验收记录固定核心/适配包身份、上游版本、数据与模型来源、命令、预算、成功与失败 Run、
评分依据、同 Run 重评和限制。涉及服务时，说明 session/host 的所有权、认证测试范围、未知副作用及清理方式。
仅拥有自己创建的资源才负责关闭，不能因为示例结束就关闭用户已有的 testbed。

活动 SQLite/CAS 和构建/训练目录放在本机合适的文件系统；所有写入者关闭后再完整归档存储。
归档后从目标位置重新读回并核验哈希，保留引用清单和必要 schema/代码身份。`output/` 下的证据归档可能仅在
原验证机器存在，且被 Git 忽略；公开报告中的路径不表示外部用户自动能够下载。公开复现仍需可分享夹具、命令和依赖。

公开前人工审核待发布的源码、文档、示例、归档与 Git 变更；打包检查不是 Git 历史或全面秘密审计。
参考答案、原始响应和日志可能敏感。不要直接删改封存证据以“脱敏”；如需公开视图，应另建经过审核的投射，
保留原证据的授权边界，不把编辑后的视图描述为原始记录。

第三方代码、数据、模型和二进制分别记录来源、固定版本与许可要求。对五份用户上传 benchmark 的
evaluation-only 限制不因导出、改名、公开投射或换训练框架而改变。来源许可未知的资产不能因位于仓库中就视为可再分发。

## 候选发行准备清单

以下是准备与复核步骤，不会自动创建 tag、上传包或发布 release：

1. 确认本次范围、版本与公共合同；从冻结基线核对差异和兼容性，更新迁移说明及变更记录。
2. 核对项目的 MIT 许可文本、版权声明和各包元数据，确保候选源码包及 wheel 包含许可文件；逐项审核新增第三方内容的独立条款。
3. 核对 README、安装路径、示例和适配包版本。检查用户不会依赖某个本机的绝对路径、私有附件或凭证。
4. 运行与变更相符的回归、隔离打包检查和必要原生验收，保存本次报告，明确条件跳过与未覆盖平台。
5. 检查最终 sdist/wheel 的清单、哈希、元数据和可选依赖；确认项目包没有进入核心 namespace。
6. 分别准备核心与本次适配包的发行制品、第三方声明和 release notes；检查其与已验证版本一致。
7. 复核拟公开的文件与附件不含凭证或受限数据，明确已知限制与安全报告入口是否可用。
8. 经仓库发布流程明确授权后，再执行实际 tag、上传或公告。当前仓库没有在本指南中定义自动发布凭证或发布工作流。

如果需要保留候选构建制品，可在**复制的源码目录**中直接调用当前 setuptools 后端，避免污染工作树：

```bash
# 先自行把候选核心源码复制到 /tmp/gymts-release-source。
cd /tmp/gymts-release-source
mkdir -p /tmp/gymts-release-artifacts
python -c 'import setuptools.build_meta as b; b.build_sdist("/tmp/gymts-release-artifacts"); b.build_wheel("/tmp/gymts-release-artifacts")'
```

独立适配包在各自源码副本中采用相同方式构建。这只产出本地制品，不发布到包索引。
正式候选仍须用检查脚本验证，不能把“成功构建”当作完整验收。

当前核心 `MANIFEST.in` 有意排除 `docs/`、`adapters/` 和本地实验输出；适配包各自发行。
完整使用文档随 Git 仓库提供，也可按[文档维护](documentation.md)构建本地静态站；
不会自动部署。教学适配包位于完整源码检出中，`examples/adapters/` 明确不进入核心发行包。
不要声称安装核心 wheel 就获得全部文档、所有项目或实验数据。
