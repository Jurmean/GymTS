# GymTS 企业内部多团队平台研发路线评审

评审日期：2026-10-16。目标由项目发起者明确为企业内部多团队共用的平台。本报告基于当前仓库、一次本地测试复核及官方项目文档的调研，提出架构与交付建议；没有修改运行代码，也没有部署外部系统。

建议把 GymTS 定位为企业 AI 平台上的时序实验与 Agent 验证层。首个共享版本帮助业务团队在获准的数据视图和任务规则下自助运行自己的方法，定位失败，并比较版本。平台团队负责共用协议、执行治理和证据关联，业务团队负责场景、方法与评价标准。

执行路线是先让两个真实业务团队完成不同工作流，再收敛公共 SDK，并接入现有作业、身份、存储和实验管理基础设施。以独立接入和重复使用作为扩展依据。已有本地运行与存储语义可以保留；字段草案作为边界检查材料，按实际工作流逐步冻结。

## 1 当前证据支持什么

2026-10-16 执行 `python3 -B -m unittest discover -s tests -q`，125 项测试通过，耗时 4.479 秒。测试证明当前适用用例内的行为，不能替代企业共享平台的隔离、规模和可运维性验证。

| 证据 | 当前判断 | 研发处理 |
| --- | --- | --- |
| 本地 Runner、持久记录、独立评分及 125 项测试 | 有可用原型和回归基线 | 保留语义与测试，分阶段迁移 |
| ChatTS 默认注册和普通文本适配继承关系 | 具体集成仍进入默认装配与复用路径 | 先修插件交付和依赖方向 |
| 本地 SQLite、文件制品与同步调用 | 适合本地研发，尚不是共享服务架构 | 保留本地模式，增加服务端实现与 worker 边界 |
| 新协议 8 组 fixture、208 条消息、10 个负例 | 有字段与调用顺序的设计证据 | 不将其当作插件安装、真实 ChatTS 或 worker 实测 |
| 既有 DeepSeek 实验报告 | 证明一条真实 API 运行、记录和重评分路径 | 不将覆盖率 Gate 通过当作业务质量通过 |
| 已检查的入口、Runner、注册器与存储 | 未见可作为多团队平台验收的工作空间授权、配额和分布式作业恢复实现 | 明确为新增平台能力，不能只给现有 Runner 套 HTTP 接口 |

本地依据：[框架入口](../gymts/__init__.py)、[默认注册](../gymts/plugins/__init__.py)、[Runner](../gymts/environment_ts/runner.py)、[存储](../gymts/storage/records.py)、[协议推演报告](contracts/pluggability-v2/validation-report.json)、本地 DeepSeek 报告 `output/experiments/deepseek-eval-2026-10-12/REPORT.md`（不随源码分发）。DeepSeek 报告明确当前 Gate 检查执行失败率和评分覆盖率，而非模型准确率。

## 2 先用业务工作流检验立项价值

建议选两个有真实负责人、可获得数据授权、会持续迭代方法的团队。以下是选择模板，不假定企业已经存在对应业务或现成数据。

| 试点 | 完整工作流 | 检验的公共能力 |
| --- | --- | --- |
| A 预测或检测团队 | 历史数据回放，运行统计方法和时序模型，未来值或人工标签到达后评价，对比新旧版本 | 时间可见性、任务窗口、方法替换、迟到依据、回测与重评分 |
| B 运维或设备诊断团队 | Agent 看异常片段，查询获准的历史和关联变量，给出判断，后续用工单或确认标签评价 | 多轮状态、工具权限、观察与请求关联、成本和失败定位 |

第二个试点必须是真实多轮工作流，不能只把预测换成另一种单轮分类。它负责检验当前抽象是否会迫使既有 Agent 重写自身控制流。第一版共享平台支持离线回放与只读查询；生产系统写操作另立验收，不把一个计数器动作样例当生产控制能力。

首轮让每个团队分别运行自己的原流程，以及基于公司现有实验与作业工具的薄适配方案。记录接入人时、手工步骤、错误定位时间和报告可信度。如果已有工具加少量适配已满足两条流程，GymTS 可以作为领域 SDK 和企业平台插件交付，独立门户和作业系统无需立项。

最关键的立项判断是：两个团队是否重复遇到同类时序实验问题，以及一套共享语义能否减少他们的工作。模型数量、schema 数量、注册项数量不能替代这个判断。

## 3 外部项目调研与复用决策

以下事实以维护者官方文档为依据。文档能确认设计与接口能力，不能证明其已满足本企业的吞吐、隔离和运维要求。右列是本次架构建议。

| 项目 | 官方材料确认的能力 | GymTS 的采用方式 |
| --- | --- | --- |
| sktime | 提供预测组合、时序切分和回测评价 | 复用基线和算法适配；不另建一套通用预测算法库。[文档](https://www.sktime.net/docs/examples/pipelines-tuning/) |
| SkyRL | 支持 Gym 风格循环，也允许自定义 Generator 接入既有 harness | 保留简单方法和原生 Agent 两种接入方式；需要训练时通过适配器输出训练合同。[文档](https://docs.skyrl.ai/docs/tutorials/agent-integration) |
| OpenEnv | 提供 Gym 风格客户端、可部署环境和容器化隔离环境 | 控制或仿真场景优先评估桥接，不自研通用沙箱；时序读取语义仍由领域合同定义。[仓库](https://github.com/huggingface/OpenEnv) |
| AgentLab | 可以运行实验，并通过 AgentXray 选择任务和步骤查看轨迹 | 借鉴从报告进入失败步骤的用户路径，不照搬网页任务的数据结构。[仓库](https://github.com/ServiceNow/AgentLab#-analyse-results) |
| MLflow | 提供实验元数据、制品与共享 Tracking Server；Workspaces 提供逻辑组织和授权 | 已有部署优先集成，复用通用实验展示和模型资产能力；GymTS 维护时序语义和其评价版本关联。[架构](https://mlflow.org/docs/latest/self-hosting/architecture/overview/)、[工作空间](https://mlflow.org/docs/latest/self-hosting/workspaces/) |
| Agent Lightning | 文档展示原生 agent harness 的训练接入、代理与作业配置 | 作为后续训练接入候选，与 SkyRL 按一个真实用例择一做适配验证，不同时绑定进核心。[文档](https://microsoft.github.io/agent-lightning/latest/) |
| Kubernetes | 提供 Job、RBAC、配额和网络隔离构件 | 已有企业作业平台优先；否则在有集群的前提下采用 Job 后端。GymTS 不另写资源调度器。[多租户](https://kubernetes.io/docs/concepts/security/multi-tenancy/)、[Job](https://kubernetes.io/docs/concepts/workloads/controllers/job/) |
| OpenTelemetry | 提供生成式 AI 调用观测约定，提醒原始输入输出敏感且体积大 | 运维链路记录状态、耗时、用量和证据引用；获准原始内容进入有授权与保留策略的制品存储。[约定](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-spans.md) |

MLflow 官方明确 Workspaces 是逻辑分隔与授权，不是硬数据隔离边界。因此可复用它的组织和展示，但工作空间映射、源数据访问以及 worker 的资源与网络边界仍需端到端核验。[来源](https://mlflow.org/docs/latest/self-hosting/workspaces/)

训练和遥测接口仍需版本验证：本次读取的 Agent Lightning 文档页面带有 development 提示，GenAI 语义约定也标记 Development。集成时选择经过测试的明确版本或提交，不把网页路径 latest 或 stable 当兼容承诺。此限制影响依赖锁定，不阻止首轮平台研发。

## 4 GymTS 应长期拥有的能力

GymTS 的领域价值应集中在以下几项：

1. 时间与信息可见性：区分事件时间、实际可用时间和决策时点；保持未来数据、迟到点、缺失点和查询范围的真实含义。
2. 可复用的任务合同：窗口、预测目标、允许的环境操作、结果含义和对齐键可以独立于模型与数据连接器复用。
3. 时序实验执行与证据：把当时看到的数据、实际方法请求、原始返回、工具回执、后到依据和本次评价关联起来。
4. 固定条件下的比较：方法版本、数据视图、案例集合、预算、评分版本和失败政策固定，缺失与无效结果显式进入报告。
5. 团队可交付的场景：把经授权的数据视图、任务、参考方法、评价政策和执行配置组织为有负责人与版本的场景模板。

SSO、通用 GPU 调度、对象存储、模型服务、通用实验仪表盘和 RL 优化器优先复用企业既有能力。新增通用基础设施必须有已测量的缺口作为依据。

领域服务也不应成为方法开发的必经重写层。业务团队可以保留自己的数据处理和 Agent 内部流程，只需在获准环境读写、输入输出与结果交付边界实现所选择的合同。

## 5 目标架构与部署边界

建议首版使用模块化单体控制服务、独立 Run worker，以及已有基础设施。Source、Task、Method 等角色是软件扩展点，不因此各自变成一个微服务。

| 层 | 主要职责 | 部署建议 |
| --- | --- | --- |
| SDK 与领域运行库 | 公共类型、可见性和能力检查、任务循环、适配服务、评价合同 | 可单独用于本地研发；业务插件在独立包或受控镜像中交付 |
| 平台控制服务 | 身份映射、授权、场景与组件目录、计划锁定、Run/Attempt、作业提交、取消与状态协调 | 一个服务起步，按负载和组织边界决定是否拆分 |
| Run worker | 加载获准插件，运行 Source/Task/Method，会话清理，提交关键证据 | 以 Run 或一组有明确边界的案例为作业；不为每次 infer 新建容器 |
| 独立评价 worker | 读取固定结果和单独授权的依据，产出新 Evaluation | 不向推理 worker 挂载私有评价标签；重评分不调用方法 |
| 企业基础设施 | 作业引擎、身份、数据权限、对象存储、数据库、模型服务、遥测与 CI | 通过少量明确适配器集成 |

这里需要调整前一轮草案的部署解释：只远程承载 Method 而让各团队 Source 和 Task 都在共享服务进程中运行，不适合作为企业隔离边界。企业 JobBackend 应承载整个 Run worker。MethodRuntime 可以继续作为 worker 内部的本地或远程方法会话机制，二者不能混成同一层调度。

共享控制服务只读取经验证的静态声明和锁定配置，不 import 或执行各团队 Python 插件。正式执行时使用已批准的包或镜像摘要、受限身份与数据授权，在 worker 中加载具体实现。

任务、方法与来源在同一可信 worker 中运行，仍不提供三者之间的强隔离。需要隔离不受信任的方法时，再配置独立方法进程或服务；接收外部任意插件之前必须完成这项隔离验证。

### 两种接入粒度

简单预测、检测和标准工具循环采用 managed 接入，复用 Source/Task/Method 的共同调度。已有复杂 Agent 采用 native harness 接入，在 worker 中保留它自己的循环，通过受控工具服务取得环境信息，提交标准结果和实际调用证据。

两种方式共享任务目标、授权、版本、预算、结果与评价合同，不强求内部推理步骤一模一样。若一个团队必须改写整个 Agent 才能接入，说明抽象或适配层需要调整；这种成本不应转嫁给每个新团队。

## 6 数据与状态如何落地

本地继续支持 SQLite 和文件制品，方便开发与最小复现。企业共享状态建议复用托管 PostgreSQL 和企业对象存储；若已有等价数据库、作业与制品服务，则适配已有系统。

GymTS 只维护必须由领域系统裁定的状态：场景及合同版本、Run/Attempt、数据授权引用、评价修订与证据关联。通用指标和报告摘要可投影到 MLflow。运行状态要有唯一裁定路径，不能让 MLflow、作业引擎和 GymTS 各自写入冲突终态。

一个可行边界是：作业后端报告 Pod/Job 事实，GymTS 的状态协调器据此与领域事件裁定 Run/Attempt，MLflow 展示其投影。模型推理失败、业务指标不达标和平台故障分别计数。

大数组和实际请求内容进入制品存储；控制数据库保存索引、摘要与关联。重叠窗口引用同一获准快照与切片定义，实际变换后发送的数组另保存必要证据，避免每个点都重复复制整段序列。原始数据可留在业务数据域，中心保存受控引用与摘要。

提交制品与提交数据库状态是跨存储操作，需要 pending/committed 状态及失败协调。只有已确认写入的对象可以发布为可用 ArtifactRef；孤儿对象按保留策略清理。关键动作意图与返回证据需要在声明的提交点持久化，不能只在 worker 正常结束时上传全部记录。

不建议首版同时建设 Kafka、数据湖、流处理引擎和复杂工作流 DSL。若将来观测吞吐和实时数据接入确有需要，使用公司已有总线或流平台，保留明确的领域适配边界。

## 7 多团队共享的上线前条件

这些是由多团队共享目标产生的必需条件，并非已经存在的能力。

| 条件 | 最小实现与验证 |
| --- | --- |
| 组织与授权 | 服务端从登录身份确定 workspace/project 和角色，不能相信客户端自报 team_id；提交、查看、取消、下载和重评分分别校验 |
| 数据用途 | 观测、训练、评价按用途授权；后到真值只提供给获准消费者，授权在执行和读取时再次检查 |
| 制品访问 | 摘要不是权限；下载经授权代理或短期凭证，工作空间前缀不是完整安全机制 |
| 运行隔离 | 团队身份、CPU/GPU/并发配额、超时、网络出口和凭证范围受控；选取与企业信任等级匹配的 worker 隔离 |
| 插件交付 | 组件有负责人、合同测试、依赖锁定和包/镜像摘要；正式目录只启用批准版本 |
| 状态可靠性 | 记录 Run 与 Attempt，取消可核对，失联 worker 有终态协调，未知操作不得被当成成功或无条件重试 |
| 证据保留 | 明确记录级别、可回放能力、访问权限和保留期；运维遥测与原始业务内容分别存储 |
| 运维责任 | 平台错误和插件错误可定位到负责人，有升级、回滚、清理与容量处理流程 |

Kubernetes 的多租户文档同时讨论 RBAC、配额、网络和数据面隔离；不能只创建 namespace 就宣布团队已隔离。网络策略还依赖支持它的 CNI。[来源](https://kubernetes.io/docs/concepts/security/multi-tenancy/)

Job 层也不提供业务恰好一次：Kubernetes 官方明确，即使单并发、单完成且 restartPolicy=Never，同一程序仍可能启动两次。因此即使关闭常规自动重试，也需将 Attempt、租约和 fencing 身份纳入运行授权；有副作用的工具服务拒绝旧持有者，必要时使用后端真正支持的幂等操作 ID。无法确认是否生效时保留 unknown 并停止自动重放。平台首轮只读，未来控制接入必须独立验证这些保证。[来源](https://kubernetes.io/docs/concepts/workloads/controllers/job/)

## 8 可复核与可重现要分别承诺

| 级别 | 能承诺什么 | 必要条件 |
| --- | --- | --- |
| 可审计 | 查清方法当时看到了什么、做了什么，结果与评分依据来自哪里 | 获准证据、身份、时间和版本关联完整 |
| 输入回放 | 对保存的同一任务输入重新调用方法 | 输入和预处理固定；远程 alias 仍可能产生不同输出 |
| 环境重演 | 从相同起点重做环境交互 | 环境可重置，初态和依赖固定，动作语义可复现 |

真实现场的重新运行不能仅因保存了日志就称为重演。原生训练数据另要求实际 token、mask、策略修订等信息；普通问答记录不能自动标成 RL rollout。

本地草案中的 strict_io 用于接口验证。企业部署应根据数据政策选择获准证据等级，并如实声明剩余回放能力。OpenTelemetry 对大体积或敏感输入输出建议默认不采集全文；本平台的运维 traces 应优先携带摘要和获准制品引用，原始内容按单独授权保存。[来源](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-spans.md)

## 9 前十二周执行计划

以下是规划估算，不是工期承诺。前提是已有或可直接使用身份、作业、数据库、对象存储和模型服务，核心投入约 4–5 人，另有两个业务负责人及共享 SRE。企业基础设施、数据授权和团队投入尚未盘点；发现缺口后必须调整范围与周期。

| 阶段 | 建议时间 | 交付 | 阶段验收 |
| --- | --- | --- | --- |
| 业务与复用验证 | 第 1–2 周 | 两份业务场景、一份现有平台能力清单、原流程基线、薄适配方案比较 | 两团队确认持续需求和负责人；明确专属领域能力及已有设施可复用范围 |
| 可执行领域内核 | 第 3–5 周 | 最小公开 SDK、外部数据插件、独立统计方法插件、ChatTS 方法适配和受控工具接口；按真实用例收敛协议 | 干净安装无 ChatTS 可运行；卸载无关插件不影响其他场景；真实输入和适配可核对；复杂 Agent 无需重写整个循环 |
| 最小共享服务 | 第 6–9 周 | 身份与授权、场景目录、Run/Attempt 服务、一个作业后端、持久证据与独立评价、基本查看入口 | 双团队授权与配额检查、跨团队访问拒绝、worker 失联/取消/重复启动等故障注入通过，业务数据经批准后才共享执行 |
| 双团队业务试点 | 第 10–12 周 | 各团队自行维护接入，持续运行、报告定位、至少两轮真实方法迭代 | 固定 SDK 版本下新增方法或来源不改核心；业务负责人可依据报告完成一次保留、回退或继续改进的判断 |

第 3–5 周无需实现字段草案里所有可选扩展。先冻结当前场景必需的观测、任务输入、响应、结果、错误与制品引用语义。把进程内调用协议与持久记录包络区分开，避免为每次本地函数调用增加无用的远程通信层。

平台授权与隔离设计在第一阶段开始；其实施必须在第三阶段的真实多团队共享前完成。不能把它们留到全员试用之后。反过来，也不应在业务需求未验证前先建设完整的大规模服务。

## 10 首批用户如何使用

首版主要使用对象应是有版本的场景模板，而不是一张需要理解全部组件的空配置表。

业务使用者选择场景、获准数据视图和自己的方法版本，检查预算后提交。平台返回排队与运行状态，结束后展示质量、覆盖率、无效结果、成本和延迟。点击失败案例，进入当时的时序窗口、允许信息、实际输出与工具返回。

开发者接入流程则是：领取模板，在自己的仓库实现 Source 或 Method，声明公共合同，运行同一套符合性测试，构建插件包或镜像，经团队负责人发布到目录。平台团队评审共用接口，业务团队维护自己的插件，不要求平台团队代写每条业务流水线。

前端优先做场景选择、运行比较和案例详情三个入口。通用参数曲线、模型列表、日志与基础监控尽量复用既有平台。AgentLab 的按实验、任务、seed 和步骤查看轨迹的流程，提供了可参考的用户路径。[来源](https://github.com/ServiceNow/AgentLab#-analyse-results)

## 11 质量工程与业务评价

继续保持当前 125 项测试作为旧协议回归基线；新增测试必须与其声称的能力对应。

| 验证类别 | 必须观察的证据 |
| --- | --- |
| 插件交付 | 核心独立 wheel、外部插件独立安装、卸载与缺失依赖错误；不靠源码目录或隐藏 PYTHONPATH |
| 跨场景符合性 | 真实来源与不同方法在同任务下的语义一致性；复杂 Agent 和简单算法共同检验接口 |
| 时间与评价 | 未来值不可见、迟到依据按截止对齐、旧报告不改写、失败和无效样本不被过滤成更好的指标 |
| 多团队授权 | API、对象存储链接、日志、缓存和重评分路径的预定拒绝用例都被执行，不能只测试列表页 |
| 生命周期 | 启动失败、模型超时、worker 退出、重复事件、孤儿制品、取消和清理失败能得到明确记录 |
| 容量与成本 | 基于真实窗口和查询负载测量排队、存储放大和执行开销，据此确定首批并发和配额 |
| 日常使用 | 业务工程师独立集成与复用的提交记录、接入人时、实际报告决策和持续迭代次数 |

业务质量门槛由场景负责人定义。预测可以按 horizon 和工况比较误差，诊断可以按确认案例比较误报、漏报、工具预算和延迟。执行成功、评价数据覆盖和业务质量必须分别报告；不能再把集成 Gate 当作统一能力评级。

首轮不预设大规模吞吐或高可用数字。先测量两条工作流的负载、数据保留成本及业务可接受恢复时间，再制定平台 SLO。模型推理耗时、第三方服务失败和平台提交延迟应分别计量。

## 12 组织分工与停止条件

平台负责人维护产品范围、SDK 与版本策略；平台后端负责人维护授权、作业和证据服务；集成工程师维护通用适配与测试工具；前端及质量工程围绕真实使用路径建设入口和故障验收。业务团队拥有自己的数据映射、任务标准、方法与 Scorer，SRE 拥有基础设施运行配合责任。

只有被两个独立业务工作流实际复用的领域概念，才优先提升为稳定公共合同。团队私有特殊字段先留在具名扩展中。正式插件记录 owner、支持版本、资源需求与维护状态，避免将共享目录变成无人维护的示例集合。

建议在第 2、5、12 周分别决策继续、缩范围或停止扩平台：

- 第 2 周仍找不到两个愿意持续投入的业务团队，先回到单团队工具交付，不为假想租户补全平台。
- 现有作业与实验平台加薄适配已满足试点需求，GymTS 以领域 SDK 或现有平台插件交付，省去独立门户和通用服务。
- 第 5 周接入第二条真实工作流仍要求修改核心或复制 Runner，回到抽象与适配边界，不继续堆功能。
- 模型或 Agent 接入要求团队重写主体控制流，补 native harness 路径或缩小支持范围。
- 第 12 周只有平台开发者持续使用，业务团队仍回到原脚本，优先排查价值、接入成本和结果可信度，不用强制迁移掩盖问题。

接入效率目标可以先设为：在数据与权限已具备、任务合同已支持的条件下，包装一个已有方法争取在一个开发日内完成。该数值是试点目标，必须与第一阶段测到的原流程基线一起调整；不适用于首次接入复杂新业务或重新训练模型。

## 13 反证审查与边界修正

| 检查点 | 主要反对意见 | 本路线的处理 |
| --- | --- | --- |
| 问题定义 | 尚未证明需要一个独立企业平台 | 以已确认的共享目标立项验证，第一阶段比较现有平台薄适配，保留 SDK 交付路线 |
| 证据分析 | schema 和本地测试不能证明生产隔离；成功示例容易围绕单一集成自证 | 区分本地证据与共享平台验收，用两个业务团队和独立插件作者检验 |
| 最终方案 | 企业化可能吞噬领域研发，训练与遥测框架也在快速变化 | 自研聚焦时序语义，通用设施优先复用；分阶段验收、依赖锁定、训练接入后置 |

最强的替代解释是：团队真正需要的是已有 MLOps 平台的时序适配，而不是新的平台产品。这一解释可以与 GymTS 作为领域层的定位共存；第一阶段必须通过实际工作流决定是否需要独立控制服务。

本报告的调查覆盖官方文档与当前代码，不包含企业现有设施、数据等级、实际人员和负载的访谈或现场验证。OpenEnv、SkyRL、Agent Lightning 等框架的适配建议尚未通过本企业环境实测；它们是候选复用方向，而非已选定且兼容的依赖。报告由 AI 辅助调研与整理，架构选择和工期估算仍需试点证据检验。
