# GymTS 项目理解

GymTS 为时序方案研发提供统一的实验执行与测试支撑。调用方用一份计划指定环境、任务、方法和运行范围，GymTS 组织观测与交互，保存结果及其证据，再在需要时使用独立评价方案生成报告。最终要支撑的是：在具体现场条件下开发 Time Series Agent，并让方案的比较、改进与交付判断有可复核的依据。

本文依据设计资料整理，并于 2026-10-12 同步正式接口规范与 AutoBenchTS 命名。字段、调用顺序和验收要求以[接口规范 1.0.0](feishu/GymTS接口规范/GymTS接口规范.md)为准。当前已实现本地同步 core 框架，入口见[项目 README](../README.md)与[框架指南](framework.md)。

## 项目目标与研发过程

研发人员需要回答的不只是某个模型在某个数据集上的指标，还包括：在什么现场、时间范围和可见信息下，哪一个版本的方法做出了什么判断或操作；后续出现了什么结果；按什么依据认为它有效，是否覆盖了所需工况。

GymTS 将这些问题组织成一条连续的证据链：

`实验计划与固定版本 → 当时观测 → 任务输入 → 原始输出 → 标准任务结果 → 后续结果 → 独立评价`

交互任务还要保留 `输出 → 操作 → 回执 → 后继观测`。这使普通算法、预训练模型、流水线和多轮 Agent 都能参与同一个实验过程，同时保留各自的原生实现和状态。

方案交付后的现场数据和生产片段可以成为下一轮实验材料。如何选择下一轮方案、组织评审和批准交付，由 LabTS 或实验调用方负责；GymTS 提供执行结果与评价依据。

## 核心模块与周边系统

| 对象 | 负责的工作 | 关键边界 |
| --- | --- | --- |
| EnvironmentTS | 装配环境、任务和方法，运行实验，组织记录，交付 RunResult | 承担运行与证据组织 |
| AutoBenchTS | 按固定案例和规则组织评价、比较基线、复用旧 Run 评分 | 使用独立结果依据，交付 EvaluationReport |
| LabTS 或调用方 | 提交实验与评价安排，选择版本，评审、批准、继续迭代 | 评价通过与发布批准分别处理 |
| LibraryTS | 保存可复用算法、模型、组件、生成器和评分实现及制品 | 通过适配按角色参与 GymTS |
| SkillTS 或已有 Agent 服务 | 提供其他工作流与方法实现 | 经统一调用契约接入本次 Run |
| Agent Platform 或现场服务 | 提供执行、权限、隔离、采集与存储等底层能力 | 具体平台需要适配，领域关联由 GymTS 组织 |

EnvironmentTS 内部再分工：Environment 连接数据或系统；Task/Binding 定义共同任务语义；Candidate 调用选定方法；Runner 组织所有调用；ExperimentRecords 保存实验关联。它们是运行层内的职责划分。

## 三类入口及其交付

`GymTS.run(ExperimentSpec)` 委托 EnvironmentTS 完成一次有边界的实验。计划包含 `scene`、`candidate`、`execution` 和 `recording`；scene 又包含 environment、task 和 binding。RunResult 用 `result_ref`、`trace_ref` 和 `artifact_refs` 交付任务结果、运行记录和产物的引用。

`AutoBenchTS.evaluate(EvaluationSpec)` 固定案例、候选与基线、评分和比较安排，生成实验计划并执行，然后汇总评价。`AutoBenchTS.score(ScoreSpec)` 复用已经存在的 Run，以本次固定的结果依据和评分版本产生新报告。

运行完成、评价达到门槛、获得交付批准分别表达。没有标签时可以完成检测或预测运行；需要真值的评分必须等待相应依据。门槛判断包含 `pass`、`fail` 和 `insufficient_evidence`，不能用零分代替缺少证据。

## 一次实验如何运行

装配时解析固定的来源、适配、任务、实现及制品版本，创建 Environment 并读取能力描述；根据 Task 描述检查 Binding 的变量、单位、时间和操作是否适用。Runner 建立记录，启动环境并保存实际会话和范围，再绑定 TaskSession、创建 Candidate，准备方法及明确授权的训练数据。

运行循环由 Runner 控制：取得并记录 ObservationBatch，交给 TaskSession.consume 构造输入和允许的反馈，按计划处理学习更新，再逐个调用 Candidate.infer。原始输出先保存并分配标识，TaskSession.interpret 再把它解释为标准结果、查询或控制请求。

查询经 Environment 返回同一 case 的下一轮输入，turn_id 递增。控制经 Environment.act 产生即时回执，后续状态与反馈通过观测回到任务。Agent 可以保留本次会话的记忆和规划状态；模型或策略更新则需要明确的学习授权。

结束标记所在的末批仍要记录并处理，保留最终状态、最后奖励和原生 terminated/truncated。达到运行边界后不再产生新的决策；若配置允许，draining 阶段仅继续读取延迟结果和处理允许反馈。之后结束方法、任务和环境会话，汇总 RunResult。Run 结束后仍可关联后到结果，原始预测保持不变。

## 环境与任务的适配边界

Environment 通过 `describe/start/observe/act/finish` 接入历史数据、合成快照、仿真器、原生 Gym 和真实系统。统一协议表达每类来源的能力、时钟、可读范围和操作含义，各后端仍保留实际的重置、延迟及可重现性差异。

字段解析属于环境适配。环境变量到公共任务变量的映射、单位换算、窗口和重采样属于 Task/Binding。方法自己的插补、特征与模型处理属于 Candidate 适配内部。采样周期不能默认暗含插值、求和或平均。

批量、流式和交互是运行方式；历史、仿真和实时是来源特性。它们需要按能力组合。例如真实系统既可能只读，也可能允许闭环控制；原生 Gym 是接口形式，其背后可能是仿真或实际设备。

## LibraryTS 与 Candidate 的关系

LibraryTS 保存可重复使用的实现，Candidate 是某个 Run 中的调用实例。接入路径是：

`固定库条目或其他实现 → Manifest 与调用适配 → Registry.resolve → Factory.create → Candidate.prepare → infer/update/finish`

实现版本、适配版本和可选模型制品版本分别记录。相同实现可以在不同 Run 使用不同参数并拥有独立状态；多个组件也可以组成一条流水线 Candidate。生成器接入环境后端，评分实现接入 Scorer，具体用途决定适配位置。

跨 Run 继承模型或记忆需要显式选择固定制品。Agent 为取得新的实验环境数据或影响实验系统而发起的请求，须经 Task 与 Runner 的路径处理，才能保持可见范围和证据关联。

## 实现时必须守住的语义

| 设计要求 | 对实现的含义 |
| --- | --- |
| 事件时间与可用时间分别保留 | 文件中存在未来值，不表示当前任务可以读取；迟到数据保留交付次序 |
| next、query、range 含义分别定义 | query 不推进主游标，读取范围和变量越权要明确报错 |
| waiting 与空窗进展分别表达 | waiting 不推进交付游标，也不能重发已经接受的动作 |
| 原生 Gym 动作与观测顺序明确 | act 调用 step 后缓存转移，observe 消费缓存；先消费再发下一动作 |
| 回执与结果分别表达 | 请求接受不代表业务目标达成；operation_id 关联事实但不承诺后端幂等 |
| 运行信息与评价依据分别授权 | 评价专用真值不能自动成为训练标签或在线反馈 |
| 原始输出与报告保留版本 | 后到真值关联旧输出；重评分生成新 evaluation_id |
| 固定引用支持复核 | 可变路径不足以固定证据，实时源必要时保存实际观测快照 |
| 会话按所有权清理 | 自建实例释放，接入真实服务只关闭自己的连接或订阅 |

记录应覆盖计划与版本、完整观测、实际输入、原始输出、标准结果、操作、回执、反馈、允许更新及制品。保存证据、用相同输入重跑方法和重新执行真实环境实验，具有不同的可重现性要求。

## 用 KPI 检测验证完整路径

[场景接入](feishu/场景接入/场景接入.md)给出了最具体的起点：server-7 的 CPU 历史数据按分钟交付，环境把 `cpu_pct` 映射为百分比变量，Binding 再转换为任务需要的比例值；Task 使用最近 60 点，每分钟产生一个检测输入；固定版本的库方法返回当前时点的异常分数。

窗口不足时只收集观测。每项分数关联实体、变量、目标时点、输入窗口和原始输出。无标签也能交付 RunResult；取得确认标签后，AutoBenchTS 将标签与已有结果对齐并评分。

据此建议首轮先打通本地回放、窗口检测 Task、一个简单 Candidate、可查询记录和独立评分。验收应能从某个异常分数追溯到具体窗口与版本，并在标签后到时完成重评分。之后再逐步加入实时只读、预测延迟结果、多轮查询和原生 Gym 控制，检验现有契约能否覆盖不同能力。这个顺序是实现建议，文档尚未指定必须采用的开发排期。
